# Свои домены магазинов и TLS

## Почему не Plesk

Plesk-nginx выпускает Let's Encrypt для доменов, заведённых в Plesk вручную.
Тысячи доменов продавцов, которые добавляются и удаляются через кабинет, так не
обслужить. Нужен on-demand TLS: сертификат выпускается при первом
TLS-рукопожатии для домена, который приложение разрешило.

## Рекомендуемая схема (открытый вопрос №5 — подтвердить у пользователя)

```
 *.shops-домен / свои домены ─► Caddy :443 (отдельный IP или сервер) ─► nado 127.0.0.1:8080
 app.<домен>, <домен>        ─► Plesk nginx (как сейчас)             ─► nado 127.0.0.1:8080
```

Caddyfile:

```caddy
{
    on_demand_tls {
        ask http://127.0.0.1:8080/internal/tls/allow
    }
    email ops@<домен платформы>
}

# Поддомены платформы — wildcard через DNS-челлендж (нужен плагин DNS-провайдера)
*.<домен платформы> {
    tls { dns <provider> {env.DNS_API_TOKEN} }
    reverse_proxy 127.0.0.1:8080
}

# Всё остальное — свои домены продавцов
https:// {
    tls { on_demand }
    reverse_proxy 127.0.0.1:8080 {
        header_up X-Forwarded-Proto https
    }
}
```

**Альтернатива без Caddy:** `github.com/caddyserver/certmagic` внутри приложения
с `OnDemand.DecisionFunc`. Минусы: приложение само слушает :443 и хранит
сертификаты (нужен `ReadWritePaths=/var/lib/nado/certs` в systemd-unit), а
перезапуск при деплое рвёт TLS-соединения. Caddy проще и надёжнее.

## ask-эндпоинт

```
GET /internal/tls/allow?domain=shop.example.kz
200 — домен есть в store_domains, verified_at IS NOT NULL, магазин активен, тариф разрешает свой домен
404 — иначе
```

- Слушается только на 127.0.0.1 (отдельный `http.Server`) или защищён проверкой
  `RemoteAddr`. Наружу его не выставлять: иначе любой узнает, какие домены
  подключены.
- Отвечает из кеша, без тяжёлых запросов: Caddy вызывает его на каждый новый
  домен.
- Без проверки через ask злоумышленник направит тысячи доменов на наш IP, и мы
  упрёмся в лимиты Let's Encrypt (50 сертификатов на зарегистрированный домен в
  неделю, ограничения на новые заказы).

## Подтверждение домена

1. Продавец вводит `shop.example.kz`. Мы нормализуем: IDNA → punycode
   (`golang.org/x/net/idna`), нижний регистр, без точки в конце. Домены платформы
   запрещены.
2. Генерируется `verify_token` (16 случайных байт, hex). Продавцу показываются
   записи:
   - `TXT _nado-verify.shop.example.kz = nado-verify=<token>`
   - `CNAME shop.example.kz → shops.<домен платформы>`. Для корневого домена
     (apex) CNAME недопустим, поэтому даётся A-запись на IP фронта.
3. Задача `domain.verify` каждые 5 минут в течение 72 часов проверяет TXT через
   `net.Resolver` с публичным DNS (1.1.1.1 / 8.8.8.8), чтобы не зависеть от кеша
   локального резолвера. Затем проверяет, что домен указывает на наш фронт.
4. Успех: `verified_at`, домен становится основным, если продавец так выбрал.
   Первый HTTPS-запрос выпустит сертификат.
5. Раз в сутки выполняется перепроверка. Если домен ушёл на другой IP, через 7
   дней он отключается, чтобы не держать сертификаты чужих доменов.

## Поддомены

`<slug>.<домен платформы>` работает без подтверждения, на wildcard-сертификате.
Правила для slug:
- `^[a-z0-9](?:[a-z0-9-]{1,61}[a-z0-9])?$`;
- зарезервированные имена: `app`, `api`, `www`, `admin`, `shops`, `mail`,
  `static`, `cdn`, `help` и т.д.;
- сменить slug можно не чаще раза в 30 дней, старый 30 дней отдаёт 301.
