## Маршрутизация по Host

Одно приложение обслуживает три вида хостов. Роутер разделяется по Host
**до** chi-маршрутов:

```go
// internal/router: hostDispatch выбирает дерево маршрутов по Host.
switch {
case host == cfg.Platform.AppHost:        // app.<домен> — кабинет продавца
    cabinet.ServeHTTP(w, r)
case host == cfg.Platform.RootHost:       // <домен> — лендинг платформы
    landing.ServeHTTP(w, r)
default:                                  // *.<домен> и свои домены — витрины
    shop.ServeHTTP(w, r)                  // middleware ResolveStore → tenant в ctx
}
```

- `ResolveStore`: `Host` приводится к нижнему регистру, порт отрезается, дальше
  поиск в `store_domains` через кеш в памяти (TTL 60 с, инвалидация при изменении
  домена). Не найден — 404 со страницей платформы, а не магазина.
- Неосновной домен магазина (поддомен при наличии своего домена) отдаёт 301 на
  `is_primary`, чтобы не было дублей для поисковиков.
- Host берётся только из `r.Host`. Заголовкам `X-Forwarded-Host` без явного
  доверенного прокси не доверяем.
- Cookie витрины ставятся на её домен без атрибута `Domain`. Сессии кабинета и
  витрины не пересекаются.

## Свои домены и TLS

Подробности: `references/custom-domains.md`. Коротко:
- продавец добавляет домен, мы выдаём TXT-запись `_nado-verify.<домен>` и CNAME
  на `shops.<домен платформы>`;
- фоновая задача проверяет DNS и ставит `verified_at`;
- сертификат выпускается on-demand: Caddy `on_demand_tls` с `ask`-эндпоинтом
  `GET /internal/tls/allow?domain=` в приложении, который отвечает 200 только для
  подтверждённых доменов.

## Темы (D-16)

Тем несколько, на старте одна или две. Подробности, включая требования сторов
приложений: `references/themes-and-apps.md`.

```
web/themes/
  base/                         базовая тема: все страницы и партиалы
    theme.json                  манифест: код, название, схема настроек (цвета, шрифты, логотип, баннеры)
    layouts/ partials/ pages/   home, catalog, product, cart, checkout, account, login, order, page, 404
    static/                     css/js; htmx.min.js локально, не с CDN
  <другая тема>/                переопределяет только нужные партиалы и страницы базовой
```

- Используется существующий `internal/view`, набор шаблонов собирается слоями:
  сначала `base`, поверх тема магазина. Одноимённый `define` из темы перекрывает
  базовый.
- Глобальные переменные шаблона: `Store`, `Theme` (настройки из
  `stores.theme_settings`), `Lang`, `Currency`, `Customer`, `InApp` (запрос из
  гибридного приложения), `T` (перевод), `Money` (форматирование).
- **Каждая тема резиновая, mobile-first.** Проверка на ширинах 360, 768, 1280,
  1920. Учитываются safe-area (`viewport-fit=cover`, `env(safe-area-inset-*)`),
  зоны касания не меньше 44 px, нет действий только по hover, нижняя навигация на
  телефоне. В режиме приложения (`InApp`) скрываются веб-элементы: баннер
  «установите приложение», футер со ссылками на сторы.
- **Каждая тема обязана иметь светлый и тёмный вариант** (D-21): режимы
  system/light/dark, переключатель на каждой странице, токены вместо цветов,
  контраст AA в обоих режимах, логотип для тёмного фона, фото товаров на
  подложке. Прежде чем верстать, загрузи скилл **nado-ui-design**.
- Настройки темы (цвета продавца для обоих режимов, шрифт) отдаются отдельным
  файлом `/_theme/vars.css?v={хеш}`. Inline `<style>` не используется: CSP
  `style-src 'self'`. Схема настроек в
  `theme.json` валидируется при сохранении в кабинете.
- htmx:
  - корзина: `hx-post` → партиал `cart-badge` + `HX-Trigger: cart-updated`;
  - фильтры: `hx-get` с `hx-push-url="true"`;
  - подгрузка «ещё»;
  - выбор варианта на карточке.
  Каждая htmx-страница работает и без JS, как обычный переход: это важно для SEO и
  доступности.
- CSP:
  - `httpx.SecurityHeaders` задаёт CSP;
  - inline-скрипты только с nonce, `htmx.config.allowEval = false`,
    `htmx.config.includeIndicatorStyles = false`;
  - сторонние скрипты (метрика продавца) — отдельная настройка магазина с явным
    расширением CSP.

## Каталог и карточка

- URL:
  - товар — `/{lang?}/p/{slug}-{id}`;
  - категория — `/{lang?}/c/{slug}`.
  `id` в URL даёт стабильность при смене slug, а при несовпадении slug отдаётся
  301 на канонический.
- Товары без доступного остатка остаются доступными по URL со статусом «нет в
  наличии», а не 404, чтобы не терять индексацию. Из листингов они уходят по
  настройке магазина.
- Доступный остаток = сумма `variant_stocks` по источникам, которые магазин
  учитывает. FBO по умолчанию не учитывается, это настройка магазина.
- Цена на витрине — `store_offers.price_minor`, её считают правила магазина или
  задаёт ручная цена (`references/pricing-rules.md`). Шаблон цену не вычисляет,
  только форматирует.
- Фильтры по характеристикам строятся из `product_attribute_values`. Запросы
  фильтрации — keyset или OFFSET с индексами по `(account_id, ...)`.

## SEO

- `<title>` и `description`: из `seo_*` перевода, иначе генерируются из названия и
  цены.
- `<link rel="canonical">` на основном домене. `hreflang` для каждого языка
  магазина плюс `x-default`.
- `/sitemap.xml` (с индексом, если больше 50 тыс. URL) и `/robots.txt` отдаются
  отдельно для каждого магазина.
- Разметка schema.org `Product` / `Offer` / `BreadcrumbList` в JSON-LD. `price`
  указывается в валюте отображения страницы.
- Скорость: изображения в нескольких размерах (`srcset`), `loading="lazy"` ниже
  первого экрана, кеш статики с версией в имени.

## Языки и валюты

Подробности: `references/i18n-currency.md`. Главное:
- язык определяется префиксом URL (`/kk/...`, `/en/...`, без префикса — язык
  магазина по умолчанию). Язык не выбирается по Accept-Language: иначе поисковик
  проиндексирует не ту версию. Accept-Language — только подсказка «переключить
  язык?»;
- валюта отображения хранится в cookie и выбирается переключателем; цены
  пересчитываются из базовой валюты по курсу дня с наценкой магазина;
- **при оформлении** покупатель видит итог в валюте списания провайдера, если она
  отличается, и курс. Заказ фиксирует обе суммы и курс.

## Корзина и оформление

- Корзина — строка `carts` с id из 32 случайных байт в cookie. Состав хранится на
  сервере, цены пересчитываются на каждом шаге, клиенту не доверяем.
- Корзину можно собрать без входа. **Оформление требует входа по телефону**
  (D-17): на шаге checkout неавторизованный покупатель видит форму входа, после
  входа корзина привязывается к `customer_id`.
- Шаги checkout:
  1. контакты: телефон уже подтверждён, e-mail необязателен (для чека в РФ нужен
     телефон или e-mail — телефон есть всегда);
  2. доставка (`delivery.Provider.Quote` и выбор ПВЗ);
  3. оплата (способы магазина);
  4. подтверждение.
- Создание заказа идёт одной транзакцией:
  - проверка остатков и цен с блокировкой (`UPDLOCK` на варианты);
  - снимок позиций, сумм и курса;
  - `orders` + `order_items` + постановка задач.
  После коммита — редирект на оплату (`payment.Provider.CreatePayment`).
- Повторная отправка формы не создаёт второй заказ: ключ идемпотентности
  checkout хранится в корзине.
- Страница заказа `/order/{number}?t={token}` защищена токеном: номер заказа
  угадывается легко.

## Покупатели

Регистрация обязательна, гостевого заказа нет (D-17). Подробности:
`references/customer-auth-otp.md`.

- Вход и регистрация — одна форма: номер телефона → выбор канала (WhatsApp или
  Telegram) → код → сессия. Паролей нет.
- Коды отправляет платформа nado одним отправителем для всех магазинов:
  пакет `internal/integration/messaging/{whatsapp,telegramgateway}` за
  интерфейсом `otp.Sender`. Генерация, хранение HMAC кода с серверным ключом
  (простой SHA от 6 цифр перебирается мгновенно), попытки и лимиты — в
  `internal/otp`, не в адаптерах.
- Защита от накрутки: лимиты на номер, IP и магазин, пауза перед повторной
  отправкой, суточный потолок. Каждое сообщение стоит денег, а злоумышленники
  используют формы OTP для toll fraud.
- Покупатель существует в пределах магазина (`UNIQUE (store_id, phone_e164)`), ПД
  видит только продавец этого магазина. Единый «nado ID» — открытый вопрос №21.
- Перед отправкой кода нужно согласие на обработку ПД: в КЗ по закону РК о
  персональных данных, в РФ — 152-ФЗ. Текст политики задаёт продавец, шаблон
  предлагаем мы.
- Кабинет покупателя: заказы, адреса, выход, **удаление аккаунта**. Удаление
  обязательно для приложений в App Store (правило 5.1.1).
- Сессия покупателя — cookie `HttpOnly; Secure; SameSite=Lax` на домене магазина.
  В гибридном приложении та же cookie внутри WebView, см. themes-and-apps.md.

## Безопасность

- CSRF: токен в cookie и в `hx-headers` на `<body>` (`X-CSRF-Token`); проверка на
  всех небезопасных методах.
- Rate limit на checkout, поиск и формы: по IP и по корзине.
- Контент продавца (описания с маркетплейсов) — HTML. Перед выводом он проходит
  санитайзер (`bluemonday` UGCPolicy). `safeHTML` на сыром описании запрещён.
