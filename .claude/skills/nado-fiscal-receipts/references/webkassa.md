# Webkassa (Казахстан) — облачная онлайн-ККМ, справочник для `fiscal.Provider`

Сведения собраны 25.09.2026. Источник — официальная Postman-документация «ИНТЕГРАТОРЫ — 2.0.4» (обновлена 26.08.2026): https://documenter.getpostman.com/view/48749526/2sBXc8o3JF. Пометка «⚠️ не проверено» означает, что факт нужно сверить.

## Модель

- Касса (ЗНК), лицензия и ОФД оформлены **на продавца**.
- Платформа как интегратор отправляет операции через API Webkassa.
- Нужны два набора данных:
  1. **API-KEY платформы.** Выдаётся техподдержкой Webkassa по запросу, отдельно для теста и для прода. Передаётся в заголовке `x-api-key` в **каждом** запросе. Хранится в конфиге платформы.
  2. **Данные продавца**, которые он вводит в нашем кабинете:
     - логин (email) и пароль пользователя-кассира Webkassa;
     - `CashboxUniqueNumber` — заводской номер кассы, ЗНК.
- `Credentials`: `{Login, Password, CashboxUniqueNumber}`, хранятся зашифрованными. Для интеграции рекомендуйте продавцу завести отдельного пользователя-кассира.

## Хосты

- Тест: `https://devkkm.webkassa.kz`.
- Прод: `https://kkm.webkassa.kz` ⚠️ не проверено. В документации показан только dev-хост; уточните при получении прод-ключа.
- Пути: `/api/v4/...`, часть методов — `/api-history/v4/...` и `/api-portal/v4/...`.

## Жёсткое правило очередности

Все запросы по одной кассе отправляются **строго последовательно**: следующий — только после ответа на предыдущий. Повторять идентичный запрос до получения ответа нельзя. Этого требует ОФД.
→ В Go: одна очередь (worker) на `CashboxUniqueNumber`. Например, джоба с блокировкой по ключу кассы в БД (`sp_getapplock` / `UPDLOCK`) или отдельный воркер с каналом на кассу. Параллельная отправка чеков на одну кассу запрещена.

## Авторизация

- `POST /api/v4/Authorize`, заголовок `x-api-key`, тело `{"Login": "<email>", "Password": "<пароль>"}`.
- Ответ: `{"Data": {"Token": "..."}}`.
- Время жизни сессии не указано. Признак истечения — ошибка `Code 2` («Срок действия сессии истек»). Кешируйте токен по подключению; при `Code 2` или `Code 3` перелогиньтесь и повторите.

## Чек — `POST /api/v4/check`

```json
{
  "Token": "...",
  "CashboxUniqueNumber": "SWK00012345",
  "OperationType": 2,
  "Positions": [{
    "Count": 1, "Price": 12500, "PositionName": "Футболка синяя XL",
    "TaxType": 100, "TaxPercent": 16, "Tax": 1724.14,
    "PositionType": 0, "UnitCode": 796,
    "Discount": 0, "Markup": 0,
    "Mark": null, "GTIN": "4600000000000"
  }],
  "Payments": [{"Sum": 12500, "PaymentType": 1}],
  "RoundType": 2,
  "ExternalCheckNumber": "c3d1e0a4-...-uuid",
  "ExternalOrderNumber": "123",
  "CustomerEmail": "buyer@example.kz",
  "CustomerPhone": "+77771234455"
}
```

- `OperationType`:
  - `2` — продажа;
  - `3` — возврат продажи;
  - `0` / `1` — покупка и возврат покупки (не нужны).
- `Positions`:
  - `Count`, `Price` — в тенге, числом.
  - `TaxType`: `0` — без налога, `100` — НДС.
  - `TaxPercent` — ставка; обязателен при `TaxType=100`.
  - `Tax` — сумма налога. Формула: `Tax = (Count*Price − Discount + Markup) × (TaxPercent/100) / (1 + TaxPercent/100)`, округление до сотых. **НДС включён в цену.**
  - `PositionName`.
  - `UnitCode` — код единицы измерения из справочника `/api/v4/references/RefUnits`. `796` — штука.
  - `PositionType` — признак ТРУ: `0` товар, `1` работа, `2` услуга. **Обязателен для протокола кассы 2.0.4+**.
  - `Mark` — код маркировки.
  - `GTIN` / `NTIN` — штрихкоды; нужны при виртуальном складе.
  - `Discount` / `Markup` — в тенге.
- `Payments`:
  - `PaymentType`: `0` — наличные, `1` — банковская карта, `4` — мобильный платёж. Для Kaspi Pay — `4`.
  - Каждый тип встречается не больше одного раза.
- `RoundType` (по умолчанию `2`):
  - `0` — позиции и итог до 2 знаков;
  - `2` — каждая позиция до целого;
  - `3` — позиции до 2 знаков, итог до целого;
  - `1` — запрещён.
  - Для интернет-магазина с ценами в целых тенге подходит `2` или `0`. Выберите один режим и покройте тестом.
- **`ExternalCheckNumber` — ключ идемпотентности**, обязателен. Генерируйте UUID один раз на документ и сохраняйте до отправки. Повтор даёт `Code 14` («Дублирующийся код системы-источника»). В этом случае получите существующий чек: `POST /api-history/v4/Ticket/GetTicketByExternalCheckNumber` (нужны `ShiftNumber` и `ExternalCheckNumber`).
- `CustomerEmail` — если указан, Webkassa сама отправит электронный чек. `CustomerPhone`, `CustomerXin` (ИИН/БИН) — необязательные.
- **Возврат продажи** (`OperationType: 3`): для протокола 2.0.3+ обязателен блок `returnBasisDetails` — реквизиты исходного чека. Храните `CheckNumber`, `DateTime`, регистрационный номер кассы и сумму исходного чека ⚠️ не проверено (точный состав полей блока; см. примеры возвратов в документации метода).
- Требования к отображению чека на казахском и русском языках касаются печатной формы, её генерирует Webkassa.

Ответ `Data`:
- `CheckNumber` (фискальный номер);
- `DateTime`, `DateTimeUTC`;
- `OfflineMode` / `CashboxOfflineMode`;
- `Cashbox{UniqueNumber, RegistrationNumber, IdentityNumber, Address, Ofd{...}}`;
- `ShiftNumber`, `CheckOrderNumber`;
- `TicketUrl` — ссылка ОФД на чек, для QR и письма покупателю;
- `TicketPrintUrl`.

Сохраните `CheckNumber`, `ShiftNumber`, `TicketUrl` и `ExternalCheckNumber`.

## Смены

- Смена **открывается автоматически** при первой операции.
- Смена **не может длиться больше 24 часов**, иначе `Code 11`. Закрывается Z-отчётом: `POST /api/v4/ZReport` с `{Token, cashboxUniqueNumber}`.
- → Ежедневная фоновая задача по каждой подключённой кассе: Z-отчёт в настраиваемое время (например, 23:55 по Алматы). При `Code 11` перед чеком закройте смену и повторите чек.
- `Code 13` — нет открытой смены. `Code 12` — смена уже закрыта. `Code 1014` — смена открыта, Z-отчёта нет.

## Коды ошибок

- `1` — неверный логин или пароль (не ретраить, пометить подключение);
- `2` — сессия истекла;
- `3` — не авторизован;
- `4` / `5` — нет доступа к операции или кассе;
- `6` — касса не найдена;
- `7` — касса заблокирована;
- `9` — ошибка валидации (не ретраить, показать продавцу);
- `10` — касса не активирована;
- `11` — смена > 24 ч;
- `14` — дубль `ExternalCheckNumber`;
- `18` — превышен автономный режим;
- `505` — сервис временно недоступен (ретрай с backoff).
- Ответ с ошибкой: `{"Errors": [{"Code": N, "Text": "..."}]}`.

## Маппинг статусов

- Синхронный ответ с `Data.CheckNumber` → `registered`.
- `OfflineMode: true` — чек сформирован в автономном режиме и будет передан в ОФД позже. Это тоже `registered`, с флагом `offline`.
- Ошибки валидации → `failed`.
- Сетевые ошибки и `505` → `pending`, повтор с **тем же** `ExternalCheckNumber`.

## Подвохи

- Последовательность запросов на кассу — главное архитектурное ограничение. Глобальный пул воркеров без ключа кассы нарушит его.
- Суммы — в тенге (не в тиынах). Конвертируйте `money.Money{Minor}` с учётом выбранного `RoundType`.
- НДС 16% — базовая ставка РК с 2026 года (в примере документации тоже `TaxPercent: 16`). Продавец не на НДС → `TaxType: 0`. Подробнее в `receipt-rules.md`.
- Если чеки продавцу уже выдаёт платёжный провайдер (например, Freedom Pay с фискализацией), не дублируйте их через Webkassa.
