## D-01. Деньги покупателей идут напрямую продавцу (BYO merchant)
**Дата:** 2026-09-25 · **Источник:** ответ пользователя

**Контекст.** Если платформа принимает деньги за продавцов, в РФ она становится
оператором по приёму платежей или платёжным агентом. Для этого нужны реестр ЦБ
(с 01.10.2024), СРО, спецсчёт, 115-ФЗ, ответственность за чеки и чарджбэки.
В КЗ нужна учётная регистрация платёжной организации в НБРК.

**Решение.** Каждый продавец подключает собственный договор эквайринга. Платформа
хранит только учётные данные для API, создаёт платежи от имени продавца и
принимает вебхуки.

**Последствия.**
- Нет лицензий, KYC продавцов и выплат.
- Под каждого провайдера пишется коннектор; продавец заключает договор сам (от дней
  до недель).
- ЮKassa подключается через OAuth-партнёрку в один клик, остальные — вводом
  ключей в кабинете.
- Платформа не видит денег, поэтому монетизация только через подписку (D-06).

## D-02. MS SQL Server остаётся основной СУБД
**Дата:** 2026-09-25 · **Источник:** решение пользователя (PostgreSQL был предложен и отклонён)

**Последствия.**
- **Express ограничен 10 ГБ на базу.** Сырые снимки карточек (`raw_json`) и
  журналы синхронизации растут быстро, поэтому храни снимок только последней
  версии, журналы чисти по сроку, медиа держи вне БД. При росте понадобится
  Standard/SPLA.
- JSON хранится в `NVARCHAR(MAX)` с `CHECK (ISJSON(col) = 1)`. Для поиска по полям
  JSON делай вычисляемые колонки с индексом.
- Полнотекстовый поиск витрины: Full-Text Search SQL Server (есть в Express with
  Advanced Services) или `LIKE` на старте. Внешний поисковый движок — только по
  необходимости.
- Очередь задач реализуется в той же БД (см. nado-go-conventions).

## D-03. Серверный рендеринг: Go-шаблоны + htmx
**Дата:** 2026-09-25 · **Источник:** ответ пользователя

Витрина и кабинет рендерятся на сервере через существующий движок `internal/view`.
Интерактивность — htmx (частичные обновления по `hx-*`), при необходимости
Alpine.js. Для витрины это важно: SEO и скорость первой отрисовки на мобильном
интернете. JSON API (`/api/v1`) остаётся для внешних интеграций и будущего
мобильного приложения.

## D-04. Магазины на поддоменах и своих доменах
**Дата:** 2026-09-25 · **Источник:** ответ пользователя

Поддомен `<slug>.<домен платформы>` обслуживается wildcard-сертификатом. Свой
домен подтверждается TXT-записью, а сертификат выпускается на лету (on-demand TLS).
Plesk-nginx так не умеет, поэтому перед витринами нужен Caddy или certmagic в
приложении на отдельном IP либо сервере. Детали — в nado-storefront
(`references/custom-domains.md`).

**Последствие для деплоя.** Схема «Plesk-nginx → 127.0.0.1:8080» из `deploy/`
подходит для кабинета и поддоменов. Для своих доменов фронт-прокси придётся
менять.

## D-05. Синхронизация каталога односторонняя: маркетплейс → платформа
**Дата:** 2026-09-25 · **Источник:** ответ пользователя

- Первичный импорт, затем периодическое обновление: цены и остатки часто
  (15–60 минут), контент редко (раз в сутки или по кнопке).
- Продажа в магазине **не** списывает остаток на маркетплейсе.
- Поля, отредактированные продавцом у нас, помечаются как переопределённые, и
  синхронизация их не трогает.

**Риск.** Возможна перепродажа, если товар одновременно купили на маркетплейсе и в
магазине. Остаток на витрине — это прогноз, а не резерв. Покажи это продавцу в
интерфейсе. Двусторонняя синхронизация — кандидат во вторую версию; интерфейс
коннектора этого не исключает.

## D-06. Монетизация — подписка по тарифам
**Дата:** 2026-09-25 · **Источник:** ответ пользователя

Тариф задаёт лимиты: число магазинов, товаров, подключённых маркетплейсов, свой
домен, число провайдеров оплаты и доставки. Проверка лимитов живёт в service, а
не в handler, чтобы API и кабинет вели себя одинаково. Сама платформа принимает
оплату подписки через свой эквайринг: рекуррентные платежи ЮKassa в РФ, в КЗ —
Freedom Pay или CloudPayments KZ. Провайдера нужно подтвердить.

## D-07. Языки RU/KK/EN, мультивалютная витрина
**Дата:** 2026-09-25 · **Источник:** ответ пользователя

- Интерфейсные строки — каталоги переводов в `internal/i18n`, контент — таблицы
  `*_translations`.
- У магазина есть **базовая валюта** (в ней импортируются и хранятся цены) и
  список **валют отображения** с конвертацией по курсу ЦБ РФ или НБРК плюс наценка
  на конвертацию.
- **Списание всегда идёт в валюте, которую поддерживает подключённый провайдер
  оплаты.** ЮKassa и Т-Касса работают в RUB, Halyk и Kaspi — в KZT.
- Чек 54-ФЗ формируется в рублях. Поэтому заказ хранит три вещи: валюту
  отображения, валюту списания и зафиксированный курс.

## D-08. Фискализация через отдельную облачную кассу
**Дата:** 2026-09-25 · **Источник:** ответ пользователя

Чеки не зависят от провайдера оплаты. В РФ используется АТОЛ Онлайн (архитектура
допускает OrangeData), в КЗ — Webkassa. Если у провайдера оплаты есть встроенные
чеки (например, «Чеки от ЮKassa»), данные чека ему **не** передаются, иначе чек
продублируется.

## D-09. Доставка: несколько служб в MVP за общим интерфейсом
**Дата:** 2026-09-25 · **Источник:** ответ пользователя

Службы в MVP: СДЭК (РФ и КЗ), Яндекс Доставка, Почта России, Казпочта, Exline и
ручные способы. Пользователь может создать собственную службу доставки вместе с
логистическим партнёром. Это будет ещё одна реализация `delivery.Provider`,
поэтому интерфейс не должен предполагать чужой API: достаточно тарифа, точек,
создания отправления и статусов.

## D-10. Импорт из Kaspi: файл и кабинет продавца
**Дата:** 2026-09-25 · **Источник:** ответ пользователя

У официального Kaspi Shop API нет чтения каталога. Реализуются два пути:
1. загрузка выгрузки (Excel или XML-прайс) — официальный запасной вариант;
2. вход в кабинет продавца — у пользователя есть рабочий пример кода из другого
   проекта. **Перед реализацией запроси этот код у пользователя**, не изобретай
   эндпоинты кабинета.

## D-11. Мультиарендность: общая БД, account_id в каждой таблице
**Дата:** 2026-09-25 · **Источник:** предложено Claude, пользователь не возражал

- Каждая арендная таблица содержит `account_id` и составные индексы, которые
  начинаются с него.
- Методы репозитория принимают `accountID` явным параметром. Взять его «из
  контекста где-нибудь внутри» нельзя: пропущенный фильтр должен быть виден в
  сигнатуре.
- Row-Level Security SQL Server (`SESSION_CONTEXT`) — возможная вторая линия
  защиты позже.

## D-12. Фоновые задачи в MSSQL
**Дата:** 2026-09-25 · **Источник:** предложено Claude

Очередь — таблица `dbo.jobs`, выборка через `UPDLOCK, READPAST`, аренда с
таймаутом, повтор с экспоненциальной задержкой. Задачу можно поставить в той же
транзакции, что и бизнес-изменение (бесплатный transactional outbox). Отдельный
брокер не нужен, пока одна БД справляется. Реализация описана в
nado-go-conventions (`references/jobs-queue.md`).

## D-13. Старт с Казахстана: сервер и юрлицо платформы в РК
**Дата:** 2026-09-25 · **Источник:** ответ пользователя

**Решение.** Платформа зарегистрирована в Казахстане, сервер стоит в Казахстане.
Первые продавцы и покупатели тоже из КЗ. Расширение в РФ решается позже.

**Последствия.**
- **Приоритет интеграций сдвигается на КЗ:**
  - маркетплейсы: Kaspi, Wildberries, Ozon (работают в КЗ);
  - оплата: Halyk ePay, Freedom Pay, Kaspi Pay;
  - чеки: Webkassa;
  - доставка: СДЭК КЗ, Казпочта, Exline.
  ЮKassa, Т-Касса, АТОЛ Онлайн, Почта России и Яндекс Доставка переносятся на
  этап выхода в РФ. Интерфейсы готовы, адаптеры пишутся позже.
- **Магазины продавцов из РФ на сервере в КЗ** означают сбор ПД граждан РФ вне РФ,
  а это нарушение ст. 18 ч. 5 152-ФЗ. Для РФ понадобится отдельная инсталляция
  в РФ (`accounts.region`), до юридической оценки российские магазины не
  запускаются.
- Партнёрская программа ЮKassa и «Каталог решений WB» для юрлица РК —
  ⚠️ не проверено, возможен ли допуск нерезидента. Проверить до работ по РФ; для
  WB в КЗ это нужно уже сейчас (open-questions №4).
- Базовые валюты: KZT по умолчанию. Язык витрины по умолчанию — ru, kk
  обязателен к поддержке с первого релиза.

## D-14. Цена в магазине: правило от цены маркетплейса плюс ручная цена
**Дата:** 2026-09-25 · **Источник:** ответ пользователя

- Цены маркетплейсов импортируются и хранятся **по каждому источнику** отдельно
  (`variant_marketplace_prices`).
- Цена в магазине вычисляется **правилом**:
  - базовая цена — цена выбранного маркетплейса или минимальная/максимальная
    среди подключённых;
  - корректировка — `−X%` или `+X%` (или фиксированная сумма);
  - округление — до 1, 10 или 100 в большую, меньшую или ближайшую сторону.
- Правило задаётся на магазин, может переопределяться на категорию и на товар.
  **Ручная цена** товара имеет высший приоритет и не пересчитывается при
  синхронизации.
- Пересчёт идёт после каждой синхронизации цен (задача `pricing.recalc`) и при
  изменении правила. Сохраняется результат (`store_offers.price_minor`) и
  источник (`price_mode`: `rule`/`manual`), чтобы продавец видел, откуда цена.
- Детали — nado-storefront → `references/pricing-rules.md`.

## D-17. Покупатели: обязательная регистрация по телефону, код через WhatsApp или Telegram
**Дата:** 2026-09-25 · **Источник:** ответ пользователя · **Меняет** «гостевой заказ по умолчанию»

- Гостевого заказа нет: для оформления нужен вход по номеру телефона.
- Одноразовый код отправляется **официальными** каналами: WhatsApp Business
  Platform (Cloud API, шаблон категории authentication) или Telegram Gateway API.
  Отправитель — платформа nado, один на все магазины.
- Учётная запись покупателя — **в пределах магазина** (`customers.store_id`).
  Продавец — оператор ПД своих покупателей, магазины друг друга не видят.
  Проверка телефона и сервис OTP — общие на платформе. Единый «nado ID» между
  магазинами — возможное развитие, сейчас не делаем (open-questions).
- Детали — nado-storefront → `references/customer-auth-otp.md`.

## D-18. Бренд nado, домены nado.kz и nado.com
**Дата:** 2026-09-25 · **Источник:** ответ пользователя; распределение по поддоменам предложено Claude

Предложенная раскладка (подтвердить при настройке DNS, open-questions №12):
- `nado.kz` — лендинг для КЗ;
- `app.nado.kz` — кабинет продавца;
- `<slug>.nado.kz` — магазины;
- `shops.nado.kz` — цель CNAME для своих доменов;
- `nado.com` — международный лендинг и будущий регион РФ/EN; до этого 301 на
  `nado.kz`.

Домены задаются конфигурацией (`PLATFORM_ROOT_HOST`, `PLATFORM_APP_HOST`,
`PLATFORM_SHOPS_HOST`), в коде не хардкодятся.

## D-19. Kaspi: основной путь — кабинет через служебного сотрудника
**Дата:** 2026-09-25 · **Источник:** референсный код пользователя (`docs/project/kaspi_samples`) · **Уточняет** D-10

- Продавец добавляет в свой кабинет Kaspi сотрудника, которого контролирует
  платформа (логин с префиксом платформы, e-mail на домене платформы).
- Код MFA приходит на почту платформы и считывается автоматически.
- Пароль продавца nado не хранит. Отзыв доступа — удаление сотрудника в
  кабинете Kaspi.
- Через кабинет nado получает каталог (`offer-view/list`), точки (`getPointList`)
  и токен официального API (`getTokenApi`).
- Импорт из файла остаётся запасным путём.
- Детали и то, что из образца **не** переносим (выключенный TLS, пароли
  открытым текстом), — nado-marketplace-import → `references/kaspi.md`.

## D-20. Онбординг Kaspi: nado сам создаёт служебного сотрудника по SMS-коду владельца
**Дата:** 2026-09-25 · **Источник:** референсный код пользователя (`lk_otp_checker.php`, `lk_otp_email_checker.php`) · **Уточняет** D-19

1. Продавец вводит в nado телефон владельца кабинета Kaspi. Kaspi присылает SMS,
   продавец вводит код в nado.
2. Короткоживущая сессия владельца используется, чтобы:
   - получить токен официального API (`getTokenApi` / `tokenGenerate`);
   - создать сотрудника `nado_<id>@<почтовый домен платформы>` через
     `user-assignments/.../add-email`;
   после чего сессия удаляется.
3. Kaspi присылает пароль сотрудника письмом на наш домен. Коды MFA при
   последующих входах тоже приходят письмом. Сервис приёма почты nado (IMAP,
   catch-all ящик) разбирает письма и сохраняет пароль и коды зашифрованными.
4. Сотруднику выдаются **минимальные роли** для чтения каталога, а не широкий
   набор ProfitBot.

**Последствия.**
- Нужна почтовая инфраструктура платформы: поддомен с MX (например
  `kaspi.nado.kz`), catch-all ящик, доступ по IMAP с TLS (open-questions №28).
- Разбор писем зависит от шаблонов Kaspi — нужны тесты на сохранённых письмах и
  алерт, если письмо не распознано.
- Детали — nado-marketplace-import → `references/kaspi.md`.

## D-21. Обязательные светлый и тёмный варианты всех страниц
**Дата:** 2026-09-25 · **Источник:** требование пользователя

- Светлый и тёмный вариант обязательны для каждой страницы: лендинг,
  кабинет продавца, все темы витрины, страницы ошибок, экраны приложений.
- Режимы: `system` (по умолчанию), `light`, `dark`. Переключатель есть на каждой
  странице. Продавец задаёт режим своего магазина по умолчанию, но не может
  отключить переключатель.
- Оформление только через семантические CSS-токены. Тема без полного набора
  токенов в обоих режимах не запускается. Контраст WCAG 2.2 AA проверяется тестом
  в обоих режимах.
- Письма остаются светлыми (`color-scheme: light only`).
- Детали — скилл **nado-ui-design**.

## D-22. Лендинг и вход продавцов: email + пароль, CSRF через CrossOriginProtection
**Дата:** 2026-09-25 · **Источник:** реализация лендинга по запросу пользователя

- **Вход продавца** — email и пароль (Argon2id, `internal/password`), серверные
  сессии в `dbo.sessions` (в БД только SHA-256 токена), cookie `HttpOnly`,
  `SameSite=Lax`, в проде `Secure` с префиксом `__Host-`. Регистрация создаёт
  пользователя, аккаунт и членство `owner` одной транзакцией (миграция 0002).
- **CSRF** — встроенный `http.CrossOriginProtection` (Go 1.25+): небезопасные
  запросы с чужого сайта и с поддоменов `*.nado.kz` отклоняются по
  `Sec-Fetch-Site`/`Origin`. Токены в формах не используются.
- **Защита форм** — ограничение частоты в памяти (`httpx.RateLimiter`, по IP и
  email) и скрытое поле-ловушка для ботов.
- **Тарифы** в коде (`service.PlanCatalog`): Старт 20 000 ₸, Бизнес 30 000 ₸
  (популярный), Про 50 000 ₸. Состав тарифов — черновик, см. open-questions №30.
- **Учебный CRUD `/api/v1/users`** из скелета в проде выключен: он не защищён, а
  в `users` теперь живые продавцы.
- Кабинет продавца пока доступен по пути `/account` на основном домене. Отдельный
  хост `app.nado.kz` (D-18) появится вместе с настоящим кабинетом.
