# Соглашения nado_go

Код уже задаёт стиль. Перед новым файлом открой ближайший аналог:
`repository/user_repository.go`, `service/user_service.go`,
`handler/api/user_handler.go`, `database/tx.go`. Пиши так же:
- комментарии на русском, объясняющие «почему»;
- ошибки оборачиваются через `fmt.Errorf("слой: действие: %w", err)`;
- без глобального состояния, зависимости передаются через конструкторы.

## Слои

```
handler  → разбор запроса, вызов service, ответ (httpx.OK/Fail, view.Render)
service  → правила, проверка прав и лимитов тарифа, транзакции, постановка задач
repository → только SQL; возвращает database.ErrNotFound / ErrConflict
integration/* → адаптеры внешних API; не знают о БД и HTTP-запросе клиента
```

- Handler не ходит в repository напрямую.
- Service не знает про `http.Request`.
- Интеграции получают расшифрованные учётные данные параметром и возвращают
  нормализованные структуры своего пакета.

Новый ресурс: `repository` → `service` → `handler/api` (`Routes()`) → `r.Mount(...)`
в `internal/router/router.go`. Зависимости собираются в `internal/app/app.go`.

## SQL и MS SQL Server

- Параметры — только `sql.Named("x", v)` и `@x` в тексте. Строка запроса —
  константа. Динамическая сортировка — через whitelist `map[string]string` колонок,
  никогда из ввода напрямую.
- Каждый метод начинается с `ctx, cancel := r.db.Context(ctx); defer cancel()`.
- Колонки перечисляются явно, `SELECT *` запрещён.
- Возврат созданной или изменённой строки — `OUTPUT INSERTED.*`-колонки, без
  повторного SELECT.
- Пагинация: `ORDER BY ... OFFSET @offset ROWS FETCH NEXT @limit ROWS ONLY` и
  `COUNT(*) OVER() AS total`. Для больших обходов (синхронизация) используй keyset
  (`WHERE id > @after ORDER BY id`).
- Upsert — `MERGE` с `HOLDLOCK`:
  `MERGE dbo.t WITH (HOLDLOCK) AS t USING (VALUES ...) AS s ...`. Без `HOLDLOCK`
  параллельные MERGE дают дубликаты или нарушение ключа.
- Пакетная вставка сотен строк: TVP (`mssql.TVP`) или несколько `VALUES` не более
  чем по ~2000 параметров. У SQL Server лимит 2100 параметров на запрос.
- Ошибки драйвера — через `database.MapError`. Сервисы сравнивают
  `errors.Is(err, database.ErrNotFound)`.
- Транзакции — `r.db.WithTx(ctx, &sql.TxOptions{Isolation: sql.LevelReadCommitted}, fn)`.
  Внутри fn используй только `tx`, не `r.db`.
- Время: `DATETIME2(3)` в UTC (`SYSUTCDATETIME()`), в Go — `time.Time` в UTC.
  Локальное время магазина — только при отображении.
- Строки пользователя: `NVARCHAR`. Коды и статусы: `VARCHAR` плюс `CHECK (... IN (...))`.
- JSON: `NVARCHAR(MAX)` + `CONSTRAINT CK_<t>_<col>_json CHECK (ISJSON(<col>) = 1)`.

## Миграции

- Файлы `migrations/NNNN_<что>.sql`, номер на 1 больше последнего. Скрипт
  идемпотентен (`IF OBJECT_ID(...) IS NULL`, `IF COL_LENGTH(...) IS NULL`), батчи
  разделены `GO`, как в `0001_init.sql`.
- Уже применённую миграцию не редактируют, пишут новую.
- Имена ограничений явные: `PK_<t>`, `FK_<t>_<ref>`, `UX_<t>_<cols>`, `IX_<t>_<cols>`,
  `DF_<t>_<col>`, `CK_<t>_<col>`. Без имени SQL Server сгенерирует случайное, и
  следующая миграция не сможет его удалить.
- Когда миграций станет больше нескольких, нужен раннер с таблицей
  `schema_migrations`. Предложи его пользователю отдельной задачей и не встраивай
  молча.

## Мультиарендность

- Арендная таблица содержит `account_id BIGINT NOT NULL` с FK. Индексы начинаются
  с `account_id`.
- Метод репозитория принимает `accountID int64` первым параметром после ctx, и в
  каждом WHERE есть `account_id = @account_id`, включая UPDATE и DELETE.
  Обращение по одному `id` без `account_id` — это уязвимость (IDOR).
- `accountID` берётся в handler из `tenant.FromContext(ctx)`: middleware кладёт его
  из сессии кабинета или из Host витрины. Service передаёт его дальше явно.
- Тест на изоляцию обязателен для нового репозитория или сервиса: запись чужого
  аккаунта не читается и не меняется.

## Деньги

- Тип `money.Money{Minor int64; Currency money.Currency}`. `Minor` — копейки или
  тиыны. В БД `BIGINT *_minor` плюс `CHAR(3)` валюты. **Никаких float.**
- Курсы — `DECIMAL(19,8)`, в Go `*big.Rat` или `github.com/shopspring/decimal`
  (уже есть транзитивно). Конвертация округляет half-up до минорной единицы, а
  результат фиксируется в заказе.
- Провайдеры принимают суммы в разных форматах: строка `"100.00"`, копейки
  числом, decimal. Конвертация живёт в адаптере провайдера, помощники — в `money`.

## Секреты провайдеров

- `provider_credentials.secret_ciphertext`: AES-256-GCM, nonce 12 байт + шифртекст.
  Ключ `SECRETS_KEY` (base64, 32 байта) задаётся в окружении. `key_version` в
  строке позволяет ротировать ключ.
- Расшифровка — в service непосредственно перед вызовом интеграции. В структурах,
  которые попадают в лог, секретов нет. Тип секрета реализует
  `slog.LogValuer`, возвращающий `"***"`.
- Вебхуки принимаются по URL `/webhooks/{provider}/{token}`. `token` — случайные
  32 байта на подключение, а в БД хранится только их хеш. Подпись провайдера
  проверяется дополнительно, токен её не заменяет.

## Фоновые задачи

Очередь в MSSQL, подробности — `references/jobs-queue.md`. Коротко:
- `jobs.Enqueue(ctx, tx, Job{Kind, Payload, RunAt, DedupKey})` в той же транзакции,
  что и изменение данных;
- обработчик идемпотентен, потому что задачу могут выполнить дважды;
- ошибка планирует повтор с backoff; `jobs.Permanent(err)` означает «не
  повторять»;
- воркеры останавливаются в `app.shutdown` до закрытия БД, как HTTP-сервер.

## Внешние HTTP API

Общий клиент `internal/integration/httpclient`. Подробности —
`references/external-http.md`. Правила:
- таймауты;
- ретраи только для идемпотентных запросов и для 429/5xx, с учётом `Retry-After`;
- лимитер на пару (провайдер, учётные данные);
- логирование с вырезанием токенов;
- сырой ответ сохраняется в ошибке для диагностики.

## Тесты

- `go test -race ./...` проходит без БД и сети. Репозитории подменяются
  заглушками, как в `router_test.go`.
- Интеграции тестируются через `httptest.Server`, который отдаёт реальные ответы
  API из `testdata/<provider>/*.json`. Ответ снимается из документации или
  песочницы, **секреты из него вырезаются**.
- Нормализация (API → доменная модель) покрывается табличными тестами: это
  самое хрупкое место.
- Тесты SQL против реальной БД помечаются build-тегом `integration` и в CI не
  запускаются.

## Конфигурация

Новые параметры добавляются в `internal/config/config.go` (с дефолтом и
валидацией), в `.env.example` и в `deploy/nado.env.example`. В prod-валидации
секреты обязательны: `SECRETS_KEY` и ключи платформы.
